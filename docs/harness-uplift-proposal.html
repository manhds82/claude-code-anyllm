1. Tổng quan & nguyên tắc

4 harness đang thấp (H2 Tool, H3 Evaluation, H5 Governance, H7 Orchestration) đều có chung một gốc: toolkit đã ship script + policy khai báo, nhưng phần thực thi cứng (enforce) nằm ở tầng server (gateway / pdp / workflow_engine) — hiện chưa deploy. Local hook chỉ là defence-in-depth (nguyên tắc C10: không quảng cáo an toàn hơn mắt xích yếu nhất).

Hệ quả chia việc: phần khai báo dữ liệu, ghi log, viết test, wiring, DAG nội bộ → dự án tự làm được ngay. Phần enforce tập trung (PDP/gateway/workflow engine, ledger anchoring, model-fallback routing) → là common, phải request Harness Toolkit vì một project không thể tự dựng hạ tầng dùng chung.

4. H2 — Tool Harness  35 → 75

Mục tiêu: mọi side-effect gọi qua registry, mang idempotency key, có audit per-call, và rate-limit được enforce.

DỰ ÁN làm được ngay

  • Đăng ký đủ side-effect của chính dự án vào contracts/tool-registry.yaml: ghi config, start/stop proxy, mở VS Code, git push trong CI, claude install — kèm schema input/output + cờ idempotent: true/false (C3 deny-by-default).
  • Gắn idempotency key qua tool-idempotency.*: ghi config keyed theo (base_url,model); start-proxy keyed theo port (đã có sẵn logic "port đang chạy → skip").
  • Audit per-call: gọi evidence-ledger ghi 1 dòng cho mỗi side-effect (định danh + hash input/output) — nâng luôn H5.
  • Test C3: thêm check policy-ci "mọi script side-effect có entry trong tool-registry" (unknown tool → fail).

REQUEST TOOLKIT (common)

  • Gateway/PDP enforce rate_limits + dedup idempotency + deny-unknown-tool ở server (một project không dựng được gateway dùng chung).
  • Idempotency store (dedup cache) dùng chung ở toolkit.
  • SDK wrapper chuẩn tự đính idempotency key + audit cho mọi tool call → project nào cũng được free.

5. H3 — Evaluation Harness  45 → 80

Mục tiêu: có golden dataset, hard-gate chặn release khi fail, và feedback loop bug→test.

DỰ ÁN

  • Tạo golden set tại .harness/eval/golden/: fixture chạy offline — ví dụ "config sinh ra là YAML hợp lệ", "toggle-brain -Status nhận đúng mode", "-List trả về danh sách model id". Mỗi case = input + expected.
  • Bổ sung test hành vi (không chỉ static) vào tests/, chạy theo vùng ảnh hưởng (mục 9).
  • Wire hard-gate cục bộ: dùng hard-gate.ps1 + skill qa-gate làm pre-push hook & job CI — fail suite ⇒ chặn push/merge.
  • Feedback loop chính thức: mỗi bug (buglist B-0x) bắt buộc kèm 1 regression test (đã áp dụng cho B-01…B-04) — biến thành policy.

REQUEST TOOLKIT

  • Release gate PDP (server-side) từ chối deploy nếu suite bắt buộc chưa PASS / report quá hạn (max_report_age_hours).
  • LLM-as-judge dịch vụ + rubric qa-gate hosted, dùng model ladder (review: Opus 4.8 → Haiku 4.5).
  • Golden-runner + schema chuẩn ở toolkit → project chỉ cần thả fixture.

6. H5 — Governance Harness  35 → 75

Mục tiêu: ledger bất biến có ghi thật, approval cho action rủi ro, risk registry sống, trả lời được "ai làm gì, lúc nào, ai duyệt".

DỰ ÁN

  • Ghi ledger thật: wire evidence-ledger vào các điểm side-effect + CI (hiện chuỗi gần rỗng). Sinh evidence-bundle (skill có sẵn) mỗi thay đổi → append ledger (DoD close-out).
  • Điền risk-registry.yaml bằng action rủi ro thật của dự án: git push repo public, start proxy kèm key, claude install — map sang approval-flow.yaml.
  • Governance bằng Git (làm được ngay): CODEOWNERS phủ .harness/** contracts/** tests/** + branch protection yêu cầu review — đây là approval "nghèo" nhưng thật.

REQUEST TOOLKIT

  • Approval workflow server-side (human-in-the-loop PDP) cho action high-risk.
  • Ledger anchoring/witness ra store WORM/notary ngoài → hash-chain mới thật sự bất biến (local chỉ tamper-evident).
  • Compliance report định kỳ như dịch vụ chung.

7. H7 — Orchestration Harness  40 → 75

Mục tiêu: DAG rõ, retry có giới hạn, fallback model, transaction rollback khi step giữa fail.

DỰ ÁN

  • Khai báo DAG nội bộ trong workflow.yaml cho luồng của chính dự án: CI (test→gate→push) và vòng agent review→fix→verify với retry bounded (max_fix_retries=5, back_to_plan=3).
  • Dùng model ladder (orchestration.model_fallback) cho các agent dự án chạy (planning/coding/review/summarization) — pin đúng C4.
  • Transaction boundary cục bộ: nếu step deploy/apply fail → harness-rollback revert working tree; step idempotent + resumable.

REQUEST TOOLKIT

  • Workflow engine (DAG executor: retry/backoff, parallel, transaction boundary, rollback-on-failure) — hạ tầng chung.
  • Model-fallback routing tại gateway (primary→fallback đa provider) để mọi agent call auto-failover.
  • Agent-to-agent protocol + state store cho handoff multi-agent.

8. Bộ Agent tự động: review → fix → UT/IT → chống hồi quy

Tận dụng tài sản đã có: .claude/agents/ (reviewer, developer, tester, devops…) + skills code-review, implement-change, fix-and-verify, verify-implementation, qa-gate. Chỉ cần ghép thành 1 vòng có kiểm soát + thêm Impact Analyzer.

AgentVai tròDựa trên
Impact Analyzer ⭐mớiTừ git diff → tính vùng ảnh hưởng + chọn ĐÚNG tập test cần chạy (mục 9)tests/impact-map.json + runner cờ -Changed
Reviewer (×3 lens)Review chỉ các hunk thay đổi: correctness / security / performanceskill code-review, .claude/agents/reviewer.md
FixerÁp fix từ finding, surgical, tôn trọng guard-zonesimplement-change, fix-and-verify
Test RunnerChạy UT/IT chỉ vùng ảnh hưởng; full ở gatetests/run-tests.*
Regression GuardSo kết quả trước/sau: chỉ được xanh hơn, cấm thêm fail mớibaseline diff + buglist policy
QA GateTrước merge/release: chạy FULL suite 1 lần + chấm rubric → APPROVED/CHANGES_REQUIRED/REJECTEDskill qa-gate, hard-gate

Luồng chạy (mỗi lần đối ứng / mỗi PR)

# bounded loop — chống "sửa cái này hỏng cái kia"
1. Impact Analyzer:  git diff --name-only  ->  vùng ảnh hưởng + tập test
2. Reviewer x3 (song song)  ->  findings (chỉ trên diff)
3. Fixer  ->  áp fix (guard-zone aware, diff nhỏ)
4. Test Runner  ->  chạy CHỈ test vùng ảnh hưởng
5. Regression Guard  ->  fail mới? -> quay lại (3), tối đa 5 lần
6. QA Gate (trước merge)  ->  FULL suite + rubric  ->  verdict
7. Ledger + evidence-bundle  ->  ghi ai/gì/khi nào

Guardrail: "không làm sai, không gây bug mỗi lần đối ứng"

  • Guard-zones (.harness/control/guard-zones.json): agent không được đụng file bảo vệ nếu chưa duyệt.
  • Regression baseline: chụp kết quả test trước khi sửa; sau khi sửa không được xuất hiện fail mới (kể cả ngoài vùng nghi).
  • Bounded retry: tối đa 5 vòng fix, 3 vòng back-to-plan → tránh loop vô hạn.
  • Bug → test bắt buộc: mọi bug phải kèm regression test (B-01…B-04 đã theo) → không tái diễn.
  • Impact-scoped để nhanh khi dev, FULL ở gate để an toàn — không đánh đổi chất lượng lấy tốc độ.

9. Test theo vùng ảnh hưởng (không test-all mỗi lần)

Cơ chế: 1 impact-map ánh xạ glob đường dẫn → tập suite/case. Runner nhận danh sách file đổi (git diff) → hợp các suite liên quan → chạy tập con. Nếu chạm file lõi/dùng chung → chạy ALL (an toàn trước tốc độ).

// tests/impact-map.json  (đề xuất)
{
  "rules": [
    { "when": ["start-claude.*"],        "run": ["policy-ci:parse,parity,config-quote", "red-team:key,secret"] },
    { "when": ["toggle-brain.*"],        "run": ["policy-ci:parse,encoding", "red-team:key"] },
    { "when": ["profiles/*.json"],       "run": ["policy-ci:profiles"] },
    { "when": ["config/*", "*litellm*"], "run": ["policy-ci:config-quote", "red-team:config"] },
    { "when": [".github/workflows/*"],   "run": ["policy-ci:workflow-yaml"] },
    { "when": ["docs/**", "*.md"],       "run": ["policy-ci:docs"] }
  ],
  "core_globs": ["tests/**", ".gitattributes", ".gitignore", ".harness/control/**"],
  "on_core_change": "ALL"
}

Runner nhận cờ mới (đề xuất): -Changed <files> / --changed <files> → resolve qua impact-map. Ví dụ dùng trong hook/CI:

# chỉ chạy test của vùng thay đổi so với main
$diff = git diff --name-only origin/main...HEAD
pwsh -File tests/run-tests.ps1 -Changed $diff        # PowerShell
bash tests/run-tests.sh --changed "$(git diff --name-only origin/main...HEAD)"  # bash
An toàn: impact-scoped chỉ dùng ở vòng dev nhanh. QA Gate luôn chạy FULL một lần trước merge/release + Regression Guard quét toàn bộ để bắt tác dụng phụ ngoài dự đoán.

11. Danh sách request gửi Harness Toolkit (common)

  1. [H2] Gateway/PDP enforce tool.rate_limits + idempotency dedup + deny-unknown-tool; kèm SDK wrapper tự đính idempotency key + audit.
  2. [H3] Release-gate PDP (chặn deploy nếu suite chưa PASS / report quá hạn) + LLM-as-judge service theo model ladder + golden-runner chuẩn.
  3. [H5] Approval workflow human-in-the-loop + ledger anchoring ra WORM/notary (biến tamper-evident thành thật sự bất biến) + compliance report.
  4. [H7] Workflow engine (DAG, retry/backoff, parallel, transaction+rollback) + model-fallback routing tại gateway + agent-to-agent protocol.
  5. [Chung] Vì các mục trên là hạ tầng dùng chung, đề nghị toolkit cung cấp dưới dạng bundle bật/tắt bằng config để mọi project kế thừa mà không phải tự dựng.

Ranh giới quyết định: nếu việc chỉ cần sửa file trong repo (data/policy/test/hook/DAG nội bộ) → Dự án làm. Nếu cần một dịch vụ chạy ngoài repo, dùng chung nhiều project (PDP/gateway/engine/notary) → Request Toolkit.
